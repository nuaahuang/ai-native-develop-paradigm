# 大模型提示词模板

## 第一步：识别待澄清问题并与用户交互

```
你是一个资深的需求分析专家，请帮我分析以下需求文档。

需求文档内容：
{requirement_doc}

请先阅读并分析这个需求文档，识别出所有需要澄清的问题。
请参考 CHECKLIST.md 中的结构化检查清单，确保覆盖以下维度：
1. 业务规则是否明确
2. 数据流向是否清晰
3. 交互流程是否完整
4. 接口与外部依赖是否确定
5. 非功能约束是否定义

在识别问题后，请逐一与用户确认这些问题的答案。

与用户交互时，请清晰描述每个问题，等待用户回答后再继续。
```

## 第二步：生成澄清后新MD文件

```
根据用户的澄清回答，请生成一份**详细完整**的澄清后新MD需求文档。

**重要要求**：必须按照 TEMPLATES.md 中的模板结构生成，确保需求分解全面准确。

请按照以下顺序组织内容：
1. 宏观能力分析
2. 页面功能映射
3. 核心数据流/页面流
4. 工作包定义（页面+前端+后端一体化）

每个工作包必须包含：
- 工作包概述（关联能力、页面、优先级、状态）
- 页面与前端视角（交互需求、UI组件、数据展示）
- 后端实现方案（核心逻辑、接口设计、数据库、技术难点、外部依赖）
- 技术难度和复杂性分析
- 工作项拆解与工时预估

请将新MD文档保存到 clarified-requirement.md 文件中。
```

## 第三步：基于新MD文档生成JSON

```
请基于刚才生成的 clarified-requirement.md 文档，进行需求项和工作项拆分，
并按以下JSON格式输出 requirement-split.json：

**⚠️ 强制规则（必须严格遵守）**：
1. 工作项是功能/模块级别的概念，不是页面级别，也不是接口级别
2. 每个工作项对应一个功能模块、卡片组件或独立功能点
3. 工时预估是该功能的总计工时
4. 前端工时和后端工时分开计算
5. 禁止输出页面名称、接口开发等工作项
6. 父级工时只能由子项计算工时汇总，禁止直接凭经验估值
7. 每个非零子项必须提供前端或后端 estimation 对象并满足计算公式
8. 必须检查通用能力是否重复计时；复用现有能力时必须降低估算

**正确示例**：
| 需求项 | 工作项（功能/模块级） |
|--------|----------------------|
| 推荐卡片展示信息内容优化 | 舌象结果卡优化 |
| 推荐卡片展示信息内容优化 | 体质结果卡优化 |
| 推荐卡片新增 | 调理方案推荐卡 |
| 报告页调理方案入口 | 食疗/舌象报告底部调理入口 |

**错误示例**：
- ❌ "食疗调理方向页"（页面级）
- ❌ "报告详情接口"（接口级）
- ❌ "入口判断逻辑"（逻辑级）

```json
{
  "requirements": [
    {
      "name": "需求项名称",
      "description": "需求描述",
      "func_type": "新增/修改/删除",
      "priority": "P0/P1/P2",
      "dependencies": ["依赖的需求项1"],
      "risk": "风险描述",
      "milestone": "M1 - 核心链路",
      "work_items": [
        {
          "name": "功能模块名称",
          "type": "页面开发/功能模块/弹窗组件",
          "level": "page",
          "backend_hours": 该页面所有后端工作的总工时,
          "frontend_hours": 该页面所有前端工作的总工时,
          "description": "说明，包含主要功能点",
          "children": [
            {
              "name": "接口或逻辑名称",
              "type": "接口开发/逻辑开发/数据设计",
              "level": "interface",
              "backend_hours": 工时,
              "frontend_hours": 工时,
              "backend_estimation": {
                "base_type": "简单接口",
                "base_hours": 1.0,
                "complexity_level": "普通",
                "complexity_coefficient": 1.5,
                "adjustment_hours": 0.0,
                "calculated_hours": 1.5,
                "reuse_status": "新建",
                "adjustment_reason": "无调整"
              },
              "frontend_estimation": null,
              "description": "说明"
            }
          ]
        }
      ],
      "notes": "注意点",
      "explanation": "澄清后的详细说明",
      "clarifications": []
    }
  ],
  "business_rules": ["业务规则1", "业务规则2"]
}
```

工时预估规则参考（采用**基准工时 × 复杂度系数**）：

| 难度等级 | 系数 | 适用场景 |
|----------|------|----------|
| 简单 | 1.0 | 单表CRUD，无业务规则 |
| 普通 | 1.5 | 少量业务规则，单表+关联 |
| 中等 | 2.0 | 多表联查，复杂业务规则 |
| 复杂 | 2.5 | 外部API对接，缓存策略 |
| 极高 | 3.0 | 分布式事务，高并发 |

**后端基准工时 × 系数**：
- 简单接口：1.0 × 系数
- 带表结构设计：1.5 × 系数
- 带字段Mock设计：2.0 × 系数
- 调用下游接口+Mock：4.0 × 系数
- 复杂逻辑功能：2.0 × N（N为综合系数）

**前端基准工时 × 系数**：
- 简单页面/布局调整：2.0/1.0 × 系数
- 表单页面：3.0 × 系数
- 列表/表格：3.0 × 系数
- 弹窗/模态框：1.0 × 系数
- 复杂交互组件：4.0 × 系数
- 动画/动效：2.0 × N（N=1-3）
- 状态管理/API对接：1.5/1.0 × 系数
- 响应式适配：2.0 × 系数

**重要**：JSON必须基于澄清后的新MD文档生成，禁止基于原始需求文档直接生成。

**强制验算**：
- `calculated_hours = base_hours × complexity_coefficient + adjustment_hours`
- 调整工时范围为 -2.0 至 2.0；非零调整必须填写具体原因
- 父级前后端工时分别等于子项对应 calculated_hours 之和
- 非零工时必须在 1.0 至 24.0 小时之间，超过24小时继续拆分
- CSV输出复杂度、估算公式、复用情况、调整原因
- 任一公式或父子汇总不成立时，终止生成并输出问题清单
```
