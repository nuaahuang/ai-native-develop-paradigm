# requirement-split Skill

## 概述

负责**需求文档的功能分解与工时预估**，采用"大模型拆解 + Python处理"的架构模式。

## 完整处理流程（12步）

| 步骤 | 执行者 | 描述 | 违背惩罚 |
|------|--------|------|----------|
| 1 | 用户 | 提供原始需求MD文档 + 设计稿 | - |
| 2 | MCP/手动 | 解析设计稿，提取页面结构、组件、交互 | - |
| 3 | 大模型 | 宏观能力分析：明确迭代核心能力 | - |
| 4 | 大模型 | 页面功能映射：建立页面与功能对应关系 | - |
| 5 | 大模型 | 分析核心数据流和页面流 | - |
| 6 | 大模型 | 工作包定义 + 技术难度和复杂性分析 | - |
| 7 | 大模型+用户 | **按 CHECKLIST.md** 识别待澄清问题并逐一确认 | ❌ 禁止跳过 |
| 8 | 大模型 | 按 **TEMPLATES.md** 模板生成 `./output/clarified-requirement.md` | ❌ 禁止跳过 |
| 9 | 大模型 | 基于新MD文档拆分需求项和工作项，预估工时 | ❌ 禁止基于原MD |
| 10 | 大模型 | 输出 `./output/requirement-split.json` | - |
| 11 | Python脚本 | 读取JSON生成 `./output/work-plan.csv` | - |
| 12 | 大模型 | 自动化验收：验证完整性和合理性 | ❌ 禁止跳过 |

**参考文件**：
- 模板格式 → [TEMPLATES.md](TEMPLATES.md)
- 提示词 → [PROMPTS.md](PROMPTS.md)
- 澄清清单 → [CHECKLIST.md](CHECKLIST.md)

### 验收规则

| 验收项 | 验证规则 | 通过条件 |
|--------|----------|----------|
| 需求项完整性 | 所有能力点都有对应需求项 | ✅ 无遗漏 |
| 工作项覆盖度 | 每个需求项至少有1个工作项 | ✅ 全覆盖 |
| 工时预估合理性 | 工时值在1.0-24小时范围内 | ✅ 符合区间 |
| 前后端关联 | 每个交互点关联到对应接口 | ✅ 关联正确 |
| 技术难点识别 | 复杂功能标注技术难点 | ✅ 已标注 |

验收失败时输出问题清单并终止流程，修改后重新验收。

### 设计稿支持

| 输入方式 | 适用工具 | 操作说明 |
|----------|---------|----------|
| Figma URL | Figma | 调用 Figma MCP 提取页面结构、组件、交互 |
| 截图/图片 | 任意工具 | 大模型视觉分析提取信息 |
| 交互描述文档 | 任意工具 | 结构化表格描述交互细节 |

### 使用方式

**方式一：仅需求文档**
用户提供MD → 宏观能力分析 → 页面功能映射 → 数据流/页面流 → 工作包定义 → 澄清（CHECKLIST.md）→ 生成澄清后MD（TEMPLATES.md）→ JSON → CSV

**方式二：需求文档 + 设计稿（推荐）**
用户提供MD + 设计稿 → 设计稿解析 → 同上流程

### 输出产物

| 文件名 | 格式 | 用途 |
|--------|------|------|
| `clarified-requirement.md` | Markdown | 澄清后的完整需求文档 |
| `requirement-split.json` | JSON | 结构化需求拆分数据 |
| `work-plan.csv` | CSV | 工作计划预估表 |

**输出目录约束**：所有产物默认保存到 `./output/` 目录下（相对于项目根目录）。

## 分解粒度标准

### 需求项（功能级闭环）
- 完整功能级别的闭环，可独立交付的业务功能模块
- 具有明确的业务价值、边界和验收标准
- 可独立开发、测试和验收

**示例**：`订单管理`、`用户注册登录`、`AI智能推荐`

### 工作项（功能/模块级）
- 对需求项的下一层级拆解，**功能模块/独立功能点**级别
- 不是页面级别，也不是接口级别
- 前后端工时分开计算

**正确示例**（来自实际项目）：
| 需求项 | 工作项 |
|--------|--------|
| 推荐卡片展示信息内容优化 | 舌象结果卡优化 |
| 推荐卡片展示信息内容优化 | 体质结果卡优化 |
| 推荐卡片新增 | 调理方案推荐卡 |
| 报告页调理方案入口 | 食疗/舌象报告底部调理入口 |
| 下单付款支付闭环 | 商品管理（纯后端代码） |
| 下单付款支付闭环 | 地址管理/添加、选择地址页 |

**错误示例**：
- ❌ "食疗调理方向页"（页面级）
- ❌ "报告详情接口"（接口级）
- ❌ "入口判断逻辑"（逻辑级）

### 分解原则

| 原则 | 说明 |
|------|------|
| 单一职责 | 每个工作项只负责一个具体功能 |
| 可测试性 | 明确的输入输出，便于测试 |
| 独立性 | 工作项之间尽量减少耦合 |
| 可估算性 | 工时在合理范围内 |

## 输入规范（JSON Schema）

```json
{
  "requirements": [
    {
      "name": "需求项名称",
      "description": "需求描述",
      "func_type": "新增/修改/优化",
      "priority": "P0/P1/P2",
      "dependencies": ["依赖的需求项1", "依赖的需求项2"],
      "risk": "风险描述",
      "milestone": "M1 - 核心链路",
      "work_items": [
        {
          "name": "功能模块名称",
          "type": "页面开发/功能模块/弹窗组件",
          "level": "page",
          "backend_hours": 后端合计工时,
          "frontend_hours": 前端合计工时,
          "description": "说明，包含主要功能点",
          "children": [
            {
              "name": "接口或逻辑名称",
              "type": "接口开发/逻辑开发/数据设计",
              "level": "interface",
              "backend_hours": 工时,
              "frontend_hours": 工时,
              "description": "接口逻辑说明"
            }
          ]
        }
      ],
      "notes": "注意点",
      "explanation": "澄清后的详细说明",
      "clarifications": []
    }
  ],
  "business_rules": ["业务规则1", "业务规则2"]
}
```

**字段说明**：
- `priority`：需求优先级，P0（核心）/P1（重要）/P2（增强）
- `dependencies`：依赖的其他需求项，决定开发先后顺序
- `risk`：技术风险或外部依赖风险
- `milestone`：所属里程碑，用于分组管理

**父子关系**：
- 父级（`level="page"`）：功能/模块级别，包含合计的前后端工时
- 子级（`level="interface"`）：接口/逻辑级别，通过 `children` 关联到父级
- CSV只输出 `level="page"` 的工作项

## 工时预估规则

### 复杂度系数

每个工作项根据实际复杂度选取系数，基准工时 × 复杂度系数：

| 难度等级 | 系数 | 适用场景 |
|----------|------|----------|
| 简单 | 1.0 | 单表CRUD，无业务规则，标准UI组件 |
| 普通 | 1.5 | 少量业务规则，单表+关联查询，表单验证 |
| 中等 | 2.0 | 多表联查，复杂业务规则，多状态交互 |
| 复杂 | 2.5 | 外部API对接，缓存策略，事务一致性 |
| 极高 | 3.0 | 分布式事务，高并发，定时任务，实时推送 |

### 后端工时

| 基准类型 | 基准工时 | 计算公式 | 示例 |
|----------|----------|----------|------|
| 简单接口 | 1.0h | 1.0 × 系数 | 简单CRUD系数1.0 = 1.0h |
| 带表结构设计 | 1.5h | 1.5 × 系数 | 多表联查系数2.0 = 3.0h |
| 带字段Mock设计 | 2.0h | 2.0 × 系数 | 含Mock系数1.5 = 3.0h |
| 调用下游接口+Mock | 4.0h | 4.0 × 系数 | 外部对接系数2.5 = 10.0h |
| 复杂逻辑功能 | — | 2.0 × N | N为综合复杂度系数 |

### 前端工时

| 基准类型 | 基准工时 | 计算公式 | 示例 |
|----------|----------|----------|------|
| 简单页面 | 2.0h | 2.0 × 系数 | 系数1.0 = 2.0h |
| 表单页面 | 3.0h | 3.0 × 系数 | 30字段表单系数2.0 = 6.0h |
| 列表/表格页 | 3.0h | 3.0 × 系数 | 含复杂筛选系数1.5 = 4.5h |
| 弹窗/模态框 | 1.0h | 1.0 × 系数 | 含表单弹窗系数1.5 = 1.5h |
| 复杂交互组件 | 4.0h | 4.0 × 系数 | 拖拽组件系数2.0 = 8.0h |
| 动画/动效 | 2.0h | 2.0 × N | N为复杂度倍数(1-3) |
| 状态管理集成 | 1.5h | 1.5 × 系数 | 系数1.0 = 1.5h |
| API数据对接 | 1.0h | 1.0 × 系数 | 含异常处理系数1.5 = 1.5h |
| 页面布局调整 | 1.0h | 1.0 × 系数 | 系数1.0 = 1.0h |
| 响应式适配 | 2.0h | 2.0 × 系数 | 多端适配系数1.5 = 3.0h |

### 计算方式

```
后端工时 = Σ(各接口基准工时 × 复杂度系数) + 逻辑复杂度调整
前端工时 = 页面基准工时 × 复杂度系数 + 交互复杂度调整 + 适配调整
```

## 输出规范

### ⚠️ 路径与文件名（必须严格遵守）

所有产出物必须保存在项目根目录下的 `./output/` 目录中，文件名固定不变：

| 文件 | 固定路径 | 生成者 | 说明 |
|------|----------|--------|------|
| 澄清后MD | `./output/clarified-requirement.md` | 大模型（步骤8） | 按TEMPLATES.md模板生成 |
| 需求拆分JSON | `./output/requirement-split.json` | 大模型（步骤10） | 作为Python脚本输入 |
| 工作计划CSV | `./output/work-plan.csv` | Python脚本（步骤11） | 读取JSON自动生成 |

**约束规则**：
- 三个文件的路径和文件名**固定不变**，不随输入内容变化
- 大模型必须将 `clarified-requirement.md` 和 `requirement-split.json` 写入 `./output/` 目录
- Python脚本默认输出到 `./output/` 目录（可通过 `--output` 参数指定）

### 输出流程

```
大模型 → ./output/clarified-requirement.md → ./output/requirement-split.json → Python脚本 → ./output/work-plan.csv
```

```
requirement-split-skill/

│   └── sample_output.json      # 示例输出
```

```bash
python scripts/requirement_split.py --input="path/to/input.json" --output="./output"
```
